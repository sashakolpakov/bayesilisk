\begin{abstract}
  Large language models can help testers explore application states that are not
  covered by ordinary end-to-end scripts, but they are unsafe as test oracles.
  They can suggest plausible scenarios, misread application semantics, and
  overstate weak evidence. \tool separates these roles. App-specific connectors
  publish observable context, available actions, and deterministic rules. First,
  \tool expands the supplied scenario space using connector-declared rules,
  action graphs, Grassmann attention, and optional model proposals. Candidate
  scenarios are then validated against connector-declared context and rules;
  malformed or unsupported proposals are rejected. Valid executable probes are
  prioritized with a Bayesian scoring procedure and run by the connector.
  Finally, \tool decides pass/fail with a deterministic ruleset over the returned
  evidence.
\end{abstract}

\section{Introduction}

End-to-end suites are precise, reproducible, and easy to trust when they fail,
but their coverage is bounded by the scenarios a test author had time to
enumerate. LLM-driven agents have the opposite shape: they can suggest unusual
states and longer workflows, but they are unreliable when asked to decide
whether the observed behavior is correct. The central design claim behind
\tool is that these jobs should be separated. Models and coding agents may help
expand the scenario space; deterministic verifier rules must remain the oracle.

This separation also changes what a test connector is expected to do. A
connector should not embed Bayesilisk-specific app logic, and Bayesilisk should
not know Cal.com-specific semantics. Instead, the connector publishes the
observable surface of the app: routes, actions, state facts, identifiers,
fixtures, expected behavior, and the evidence observed after a probe executes.
\tool then generates candidate scenarios, rejects candidates that do not fit
the connector contract, prioritizes executable probes, and verifies returned
evidence against deterministic invariants. Each concrete scenario can be
sampled from the declared scenario space with priority informed by proximity to
contract boundaries, selected invariant planes, and suspected violations.

The intended workflow is:

\begin{enumerate}
    \item A connector publishes app-specific context: routes, actors, identifiers,
          available actions, state facts, nearby tests, and expected behavior.
          This context defines the executable surface that Bayesilisk is allowed
          to reason about.
    \item \tool constructs a candidate scenario space from connector-declared
          rules, mutation operators, action graphs, and optional model-proposed
          scenarios. LLM output is treated only as candidate input, never as an
          oracle.
    \item Candidate scenarios are validated against the connector contract. A
          scenario that references unknown routes, actions, identifiers,
          invariants, missing state facts, unsupported parameter bindings, or
          undeclared expected behavior is rejected as malformed or unsupported.
    \item Valid executable probes are prioritized. Grassmann-style attention
          routes search toward nearby invariant planes and contract boundaries,
          while Bayesian scoring ranks candidates by estimated fault probability.
    \item The connector executes selected probes through the real app, a local
          test harness, or Playwright/API fixtures. The connector reports observed
          evidence such as statuses, URLs, state transitions, traces, screenshots,
          and execution errors. It does not decide whether the behavior is a bug.
    \item \tool verifies the returned evidence against deterministic invariants.
          Only evidence-bearing probes that violate declared rules become
          issue-ready findings; malformed proposals and unsupported executions are
          recorded as proposer or connector telemetry, not product bugs.
\end{enumerate}

The connector is app-specific. The \tool core is not. This boundary is the main architectural point: app teams write connectors that expose context, actions, and evidence; \tool provides the generic scenario expansion, validation, prioritization, and deterministic verification loop.

\section{Architecture}

The architecture has four trust boundaries.

\begin{enumerate}
  \item \textbf{Scenario proposal is untrusted.} Connector-declared mutation
        rules, connector action graphs, and optional LLM proposals all produce
        candidate scenarios. A candidate is not yet an executable probe, and it
        is never an oracle.
  \item \textbf{Validation is local and deterministic.} Before execution,
        \tool checks that every candidate references declared routes, actions,
        parameters, state facts, and invariants. Unsupported candidates are
        rejected and recorded as proposer telemetry.
  \item \textbf{Execution belongs to the connector.} The connector maps a valid
        proposal to concrete app operations: Playwright navigation, API calls,
        fixture setup, database state, login/session actions, screenshots, or
        traces. The connector returns evidence; it does not decide pass/fail.
  \item \textbf{Verification belongs to \tool.} \tool compares returned evidence
        with deterministic invariants. Only evidence-bearing violations become
        issue-ready findings.
\end{enumerate}

Grassmann-style attention and Bayesian scoring operate between validation and
execution. They choose which valid probes to run first; they do not decide
truth. This matters for LLM integration. A weak model may produce an
interesting-looking scenario that references an unavailable action or an
undeclared invariant. Bayesilisk should reject such a candidate as malformed or
unsupported, not send it to the app and not report it as a product bug.

\section{Cal.com Case Study}

We evaluated the current connector architecture on a local Cal.com checkout.
The tested repository and revision were:

\begin{itemize}
  \item Repository: \url{https://github.com/calcom/cal.com}
  \item Commit: \texttt{180ede28f0bddf2738933a6e60a8e80f6116d7da}
  \item Commit date: \texttt{2026-05-14 19:30:21 +0000}
  \item Commit subject: font-stack fallback fix for non-Latin script support
        (\texttt{\#29346})
  \item Bayesilisk seed: \texttt{150}
\end{itemize}

The connector supplied route facts for Cal.com booking pages and an action graph
for a longer booking workflow. From this context, \tool generated seven probe
proposals. Six probes mutated unknown or stale \texttt{rescheduleUid} values on
public, private, and dynamic booking routes. The seventh probe was a generated
workflow sequence: create a booking, cancel it, then replay the cancelled
booking UID through the public booking route as reschedule context.

The checked-in Bayesilisk artifacts are in \texttt{examples/calcom/}. They
include the connector, source contexts, generated proposals, consolidated
execution context, app-only JSON report, app-only Markdown report, issue
payloads, and the two Playwright run logs for the clean rerun.

The Cal.com evaluation also included comparison runs against nearby E2E tests,
manual Playwright-style probing, weak local model proposal generation, and a
browser-driving LLM-agent baseline. These comparisons are not used as the
oracle; they are included to explain why the Bayesilisk split is useful.

The nearby upstream E2E tests did not expose the seven Bayesilisk findings. The
Playwright-only connector checks did expose part of the same bug family, but
they did not produce the full unknown/stale Cartesian expansion across all
declared routes. The weak-model proposal run is a negative result: plausible
model text did not satisfy the verifier gates, so it was rejected before it
could become an app finding. The browser-driving LLM-agent baseline illustrates
the oracle problem directly: in repeated local trials, the agent sometimes
selected malformed or unusable actions and sometimes disagreed with the
deterministic expected-vs-observed verdict. This is the behavior \tool is
designed to contain.

\section{Upstream Response}

Two upstream issues were opened from this evidence: one for public
\texttt{rescheduleUid} replay~\cite{calcomIssue} and one for cancelled booking
UID replay~\cite{calcomCancelledIssue}. The first issue already has a
human-authored fix pull request~\cite{calcomFixPr}. This is stronger validation
than issue closure alone: an issue can be closed as erroneous, but a targeted
fix PR indicates that a human contributor found the report actionable.

The upstream response is important because the claim is not only that
\tool can emit plausible reports. The reports need to be useful to humans
working on the target system.

\section{Discussion}

The evidence supports a concrete but bounded claim. Given connector-supplied
source facts, rules, and action graphs, \tool can expand a scenario space,
reject malformed proposals, prioritize executable probes, run them through an
app-specific connector, and verify evidence without letting an LLM decide the
outcome. This is different from a plain Playwright script because the connector
does not enumerate every final generated probe by hand; it exposes the local
state and rule space, and \tool produces the concrete mutations and the bounded
workflow sequence.

The current sequence proposer is intentionally limited. It composes short
sequences from declared actions and state facts; it does not synthesize
arbitrary free-form browser sessions. That limitation is a design boundary, not
a defect: the connector remains a small executor, while the core remains
app-agnostic. A stronger generality claim will require additional real-app
artifacts with the same discipline: exact repository revision, connector code,
context JSON, generated proposals, execution evidence, deterministic report,
issue payloads, and upstream response where available.

\section{Conclusion}

\tool treats LLMs as scenario proposers, not as test oracles. The Cal.com case
study shows the architecture working on a real app checkout: seven generated
probes, seven connector-observed failures, deterministic issue payloads, and an
upstream human-authored fix PR for one reported finding. The broader lesson is
that LLMs can help search the scenario space, but the oracle must remain a
deterministic verifier over evidence returned by an app-specific connector.
