\begin{abstract}
Large language models can enlarge the scenario space explored by end-to-end tests, but they are unsafe as test oracles: they can invent impossible states, misread application semantics, and overstate weak evidence. Bayesilisk separates scenario proposal from verification. App-specific connectors publish a bounded search surface consisting of routes, actions, identifiers, state facts, invariants, and executable probe hooks. The Bayesilisk core expands that surface into candidate scenarios, rejects malformed candidates by deterministic contract validation, prioritizes valid probes with Grassmann-style attention and a Bayesian score, and verifies only evidence returned by connector execution. The same boundary supports coding-agent assistance: agents may draft connector context, action mappings, and repair briefs, but cannot author observations, pass/fail results, or issue readiness. The reusable search surface is a library of category-theory motifs: abstract tokens are objects, connector actions are morphisms, and each connector is a functor to its concrete application; a deterministic scanner derives the surface from an API description, and a stateless loop controller drives motif binding, verification, and repair to convergence while the oracle stays deterministic.

This paper gives a compact formal model for that loop and reports a Cal.com case study at a fixed May 2026 revision. From connector-declared route facts and a typed Abstract Bayesilisk Action Graph (ABAG), Bayesilisk generated seven probes. All of them returned deterministic expected-vs-observed violations. One upstream report has a targeted fix pull request that identifies the root cause and adds a regression Playwright test; an independent human reviewer approved that fix.
\end{abstract}

\section{Introduction}

End-to-end suites (E2E) are reliable when they fail because their assertions are
explicit, executable, and repeatable. However, their weakness is coverage. A suite usually contains the workflows a team remembered to encode under the time and productivity constraints, not the combinatorial neighborhood around stale identifiers, role changes, cancelled state, direct routes, private links, feature flags, or replayed workflow tokens.

On the other hand, LLM-driven browser agents have the opposite shape. Prior work
shows that language models can interleave reasoning and external actions, but
realistic web-agent benchmarks still show large reliability gaps, and
hallucination remains a known failure mode in generated text and
reasoning~\cite{react,webarena,ji2023hallucination}. Such agents can suggest
unusual states and longer sequences, but they are unreliable when asked to decide
whether the observed behavior is correct. They also cannot guarantee reliable
generation of valid scenarios.
Recent agentic E2E work still asks the inherently stochastic model to infer
pre/postcondition oracles~\cite{webtestpilot}; \tool instead keeps the oracle
within deterministic connector-supplied bounds.

\tool~\cite{bayesilisk} is built around a narrow separation: models propose where to
look, but deterministic rules decide what counts as a valid scenario, and what
constitutes a failure. Ranking is a later triage step, not an oracle. The
connector for an application exposes context and executable hooks; it does not
own the scenario search strategy. The \tool core generates candidate scenarios
from the declared surface, validates candidates against the connector contract,
ranks valid probes, asks the connector to execute them, and verifies returned
evidence against explicit invariants.

The workflow form of this boundary is an Abstract Bayesilisk Action Graph
(ABAG). In an ABAG, \tool sees typed abstract tokens such as
\texttt{resource.public\_id}/\texttt{booking}; the connector/adaptor supplies
refinements such as \texttt{booking.uid} so the abstract proposal can be
executed in the concrete application.

This is close in spirit to property-based testing, where generators produce
inputs and properties act as oracles~\cite{quickcheck}. The difference is the
target: \tool treats a modern UI/API application as the system under test and
uses browser/API probes, implemented in the artifact with Playwright, as
evidence sensors~\cite{playwright}. It also treats LLM proposals as untrusted
generator hints, not as properties and not as verdicts.

The practical value is that teams do not have to choose between narrow E2E
scripts and unconstrained LLM agents. If a team can describe the app surface it
already understands---actors, routes, actions, fixtures, identifiers, and
rules---\tool can sweep the adjacent scenario space, prioritize suspicious
combinations, and emit deterministic issue payloads. Our claim is deliberately
bounded but useful: \tool does not replace domain knowledge; it turns that
domain knowledge into a larger, more variable, and repeatable search procedure.

This paper makes five contributions:

\begin{enumerate}
  \item a trust-boundary model for using LLM-proposed scenarios without using an
        LLM as the oracle;
  \item a mathematical formulation of connector contracts, scenario validation,
        Grassmann-style attention, Bayesian ranking, and deterministic
        evidence verification, including typed ABAG workflow composition and a
        category-theoretic motif library (abstract tokens as objects, connector
        actions as morphisms, connectors as functors);
  \item a Cal.com artifact showing seven generated probes, seven observed
        expected-vs-observed violations, reproducible issue payloads, and an
        upstream targeted fix pull request with human approval review for one
        reported issue;
  \item a deterministic API-surface scanner and a stateless loop controller that
        automate scan, motif binding, execution hand-off, verification, and
        repair to a bounded convergence criterion, keeping the oracle
        deterministic throughout; and
  \item an explicit account of scope and generalization: connectors are
        app-specific by design, action-sequence breadth is governed by the
        connector-declared graph, and the Cal.com comparison runs validate the
        architectural separation from E2E-only, Playwright-only, weak-model, and
        LLM-agent workflows.
\end{enumerate}

\section{Claim Audit}

There are four important questions to be answered about \tool, including its architecture and use cases.

\textbf{Who generates scenarios?} The connector declares the app-specific search
surface: routes, actions, identifiers, state facts, invariants, and valid
mutation or action schemas. For workflow probes, it declares a typed ABAG:
actions, abstract token preconditions, abstract token products, state
requirements, and connector refinements. \tool generates concrete candidate
scenarios from that declared surface, optionally using LLM proposals as
additional candidate ideas. The connector does not enumerate final tests.

\textbf{Who executes scenarios?} The connector executes validated probe requests
through the real application, local fixtures, Playwright, API calls, or a test
harness. It returns observed evidence such as semantic status, URL, trace,
screenshot, state transition, or execution error.

\textbf{Who decides pass or fail?} \tool decides pass/fail by applying
deterministic invariants to evidence returned by the connector. Neither the LLM nor the
connector is the oracle.

\textbf{How can coding agents participate safely?} A coding agent may help
collect connector requirements, draft source context, write connector code in
the target repository, and propose repairs after a verified finding. Those
steps are admissible only when provenance is recorded and verifier-owned fields
are kept out of agent-authored artifacts. Scenario plans cannot contain
\texttt{observedStatus}, \texttt{passed}, risk scores, or issue readiness.
Observed evidence is admitted only after connector execution against local
fixtures. Repair briefs are derived from verified issue-ready findings, not from
raw connector output.

\textbf{What external validation exists?} The Cal.com artifact produced
issue-ready findings. One public issue, \#29399~\cite{calcomIssue}, has an
upstream contributor fix pull request, \#29400~\cite{calcomFixPr}, that
identifies a missing null guard in \texttt{processReschedule} and adds a
regression Playwright test. The fix PR has a human approval review that calls
the null guard correct and the test coverage solid~\cite{calcomFixReview}. A
separate workflow issue thread, \#29407~\cite{calcomCancelledIssue}, remains
open at capture time.

\section{Formal Model}

Let an application connector publish a contract
\[
  C = (R, A, F, I, M, G),
\]
where \(R\) is a set of route patterns, \(A\) is a set of connector actions,
\(F\) is a set of observable state facts and identifiers, \(I\) is a set of
deterministic invariants, \(M\) is a set of parameter mutation schemas, and
\(G\) is an Abstract Bayesilisk Action Graph. The connector is app-specific; the
\tool core is a generic function over \(C\). In this sense the connector is an
application adaptor: it translates between concrete app fixtures and the
abstract contract consumed by \tool.

\subsection{Scenario Generation and Validation}

From connector-declared route facts and mutation schemas, \tool constructs a
route-mutation candidate of the form
\[
  s = (r, a, i, p, m),
\]
where \(r \in R\) is a declared route pattern, \(a \in A\) is a declared
connector action, \(i \in I\) is a declared invariant, \(p\) is a declared route
parameter, and \(m \in M(p)\) is an allowed mutation for that parameter, such as
unknown, stale, foreign, missing, or duplicate. The connector does not enumerate
this final candidate. It declares the searchable surface and the allowed
mutation schema; \tool performs the expansion, deduplication, validation, and
ranking.

\subsection{Abstract Bayesilisk Action Graphs}

For longer workflows, \tool uses a typed Abstract Bayesilisk Action Graph
(ABAG)
\[
  G = (A,T,\operatorname{req},\operatorname{prod},\operatorname{bind}),
\]
where \(A\) is the connector action set and \(T\) is a set of typed tokens. A
token \(\tau \in T\) has three relevant fields:
\[
  \tau = (u,c,\rho).
\]
The components deliberately separate the portable abstraction from the
app-specific adaptor vocabulary:
\begin{itemize}
  \item \(u\) is the universal token, for example
        \texttt{resource.public\_id} or \texttt{state.cancelled};
  \item \(c\) is an optional class that narrows the token, for example
        \texttt{booking}, \texttt{event\_type}, or \texttt{calcom\_user};
  \item \(\rho\) is an optional concrete connector refinement, for example
        \texttt{booking.uid} or \texttt{user.username}.
\end{itemize}
The abstract key used by the \tool core is
\[
  \kappa(\tau) = (u,c).
\]
The refinement \(\rho\) is not used to satisfy graph dependencies. It is
connector-facing metadata that lets the adaptor execute a generated abstract
probe against concrete fixtures.

Each action \(a\in A\) has required and produced token sets,
\(\operatorname{req}(a)\subseteq T\) and
\(\operatorname{prod}(a)\subseteq T\). A sequence
\[
  \sigma = (a_1,\ldots,a_k)
\]
is valid for a terminal goal action \(a_k\) only if
\[
  \forall t \in \{1,\ldots,k\}:
  \{\kappa(\tau):\tau\in\operatorname{req}(a_t)\}
  \subseteq
  \bigcup_{j<t}\{\kappa(\tau):\tau\in\operatorname{prod}(a_j)\},
  \qquad k \le d_{\max}.
\]
Goal parameter bindings are also typed. If a terminal action has a parameter
\(p\), then \(\operatorname{bind}(a_k,p)=\tau\) means that \tool may bind
\(p\) to a previously produced token with the same abstract key \(\kappa(\tau)\).
If \(\rho\) is present, \tool emits it in the generated proposal so the
connector can look up the concrete value. Thus \tool may reason over
\texttt{resource.public\_id}/\texttt{booking}, while the Cal.com connector
executes with \texttt{booking.uid}. This is the central refinement boundary:
Bayesilisk composes and validates over abstract tokens; the connector/adaptor
executes concrete app operations through refinements.

This makes the reusable unit a graph motif rather than an app noun. The same
abstract sequence
\[
  \texttt{resource.create}
  \rightarrow
  \texttt{state.transition(revoked)}
  \rightarrow
  \texttt{identifier.replay(boundary)}
\]
can describe cancelled booking replay, voided invoice link replay, expired
password-reset token replay, or revoked invitation acceptance. Each app needs
its own connector refinements and execution hooks, but the \tool core sees the
same class of verifier-search problem.

Validation is deterministic:
\[
  V_C(s) =
  \begin{cases}
    1 & \text{if every referenced route, action, parameter, fact, token, and
         invariant is declared in } C,\\
    0 & \text{otherwise.}
  \end{cases}
\]
Only candidates with \(V_C(s)=1\) can become executable probes. LLM output enters
the same validation gate. Unknown target planes, unknown ids, duplicate
proposals, non-string fields, malformed JSON, impossible counts, and unsupported
actions or ill-typed ABAG tokens are rejected as proposer telemetry rather than
reported as product failures.

\subsection{Motifs as a Category}

The reusable search surface is organized as a small category \(\mathcal{A}\).
Objects are abstract token keys \(\kappa(\tau)=(u,c)\); the generating morphisms
are connector actions \(a\), with domain
\(\{\kappa(\tau):\tau\in\operatorname{req}(a)\}\) and codomain
\(\{\kappa(\tau):\tau\in\operatorname{prod}(a)\}\), and composition is the valid
sequencing above. A \emph{motif} is a typed obligation in \(\mathcal{A}\). A
parameter motif is an arrow from a single object to an expected status, e.g.\
\(\texttt{resource.public\_id}(\text{absent})\to 404\); a workflow motif is a
composite morphism whose adversarial path must \emph{not} commute into success,
e.g.\ \(\texttt{create}\to\texttt{cancel}\to\texttt{replay}\) must reach
\(409\), not \(200\). A connector is a functor \(F:\mathcal{A}\to
\mathcal{C}_{\mathrm{app}}\) into the concrete application: it sends each object
to a fixture or route through the refinement \(\rho\) and each morphism to an
executable action. \tool reasons only in \(\mathcal{A}\), matching by \(\kappa\)
and never by \(\rho\); functoriality is exactly the refinement boundary above~\cite{maclane}.
Motifs are grouped into versioned packs over the universal vocabulary. Binding a
pack to a contract \(C\) instantiates each motif's arrows as concrete candidates,
route mutations or ABAG sequence rules, that re-enter the same validation and
verification path; nothing in the oracle changes. The motifs distilled from the
case study below---unknown, foreign, and wrong-parent identifiers,
cancelled-state replay, superseded tokens, and missing sub-resource
references---are such app-agnostic arrows and apply to any app through its own
\(F\). Packs are tiered (an open core pack and optionally gated packs verified by
an offline signature); tiering is a distribution concern and does not touch
verification.

\subsection{Grassmann Attention}

The attention layer is a prioritizer, not an oracle. Conceptually, invariant
descriptions and observations define local subspaces in a feature space. For an
invariant plane \(P_i\) and context vector \(q\), a Grassmannian proximity score
can be written as
\[
  \gamma_i(q) = \|\Pi_{P_i} q\|_2^2,
\]
where \(\Pi_{P_i}\) projects \(q\) onto the invariant plane. This follows the
standard geometric view of subspaces on Grassmann manifolds~\cite{edelman1998geometry}.

However, \(\gamma_i(q)\) is only an ideal geometric score. The current
implementation does not compute this projection directly. Instead, it uses an
interpretable bounded anchor-plane proxy, \(\alpha_i\), whose novelty term can
include embedding similarity to the same invariant-plane anchors. Thus
\(\alpha_i\) is the operational attention score used for ranking planes in the
current artifact, while \(\gamma_i\) describes the intended Grassmannian
interpretation. For each invariant~\(i\), \tool computes
\[
  \alpha_i =
  \operatorname{clip}_{[0,1]}
  \left(
      w_f f_i + w_u u_i + w_s \sigma_i + w_p p_i + w_n n_i - d_i
  \right),
\]
with current weights
\[
  (w_f,w_u,w_s,w_p,w_n)=(0.45,0.25,0.15,0.10,0.05).
\]
The variables are computed directly from context facts. The notation is:
\(P_i\) is the invariant plane; \(q\) is the context vector; \(\Pi_{P_i}\) is
projection onto \(P_i\); \(\gamma_i(q)\) is ideal Grassmann proximity;
\(\alpha_i\) is the operational attention score; \(T_i\) is the number of facts
whose \texttt{invariantId} is \(i\); \(F_i\) is the number of those facts that
fail; \(N_i^{PW}\) is the number of those facts whose source is
Playwright; \(K_i\) is the keyword-hit count; \(E_i\) is
embedding similarity; \(\sigma_i\) is configured invariant sensitivity; and
\(d_i\) is fixed/muted decay. The normalized feature names are: \(f_i\) for
failure density, \(u_i\) for untestedness, \(p_i\) for Playwright evidence, and
\(n_i\) for novelty.

The current artifact uses three saturation thresholds:
\[
  \tau_T=4,\qquad \tau_P=3,\qquad \tau_K=6.
\]
They are calibration constants, not oracle rules. \(\tau_T\) means that after
four observations a plane is no longer treated as materially untested;
\(\tau_P\) means that three Playwright observations saturate the browser-evidence
term; and \(\tau_K\) means that six keyword hits saturate lexical novelty.
These values are current implementation defaults chosen to make attention
saturate quickly on small connector artifacts; they should be treated as tunable
ranking parameters and ablated in larger evaluations. Changing these thresholds
changes prioritization pressure only; it does not change candidate validity or
pass/fail verification. Then
\[
  f_i =
  \begin{cases}
    F_i/T_i & T_i>0,\\
    0 & T_i=0,
  \end{cases}
  \qquad
  u_i =
  \begin{cases}
    1 & T_i=0,\\
    \max(0,1-\min(T_i,\tau_T)/\tau_T) & T_i>0,
  \end{cases}
  \qquad
  p_i=\min(1,N_i^{PW}/\tau_P).
\]
In the current artifact, the sensitivity \(\sigma_i\) is read from the
\texttt{INVARIANT\_SENSITIVITY} table maintained by the \tool authors in the
core configuration. It encodes how sensitive an invariant plane is considered
for search prioritization. If an invariant id is absent from that table, as may
be the case for connector-supplied external invariants, the implementation uses
the neutral default \(0.5\). The novelty term is
\[
  n_i=\max(\min(1,K_i/\tau_K),E_i),
\]
where \(K_i\) is the context keyword-hit count for invariant \(i\), and
\(E_i\in[0,1]\) is optional embedding similarity to the invariant anchor plane
(\(0\) if embeddings are disabled or unavailable). The decay \(d_i\) is \(0.12\)
for fixed or regression-watch invariant ids, \(0.20\) for muted invariant ids,
and \(0\) otherwise, using the larger value if both apply. The largest
\(\alpha_i\) values select planes for exploration. They do not determine whether
a behavior is correct.

\subsection{Bayesian Ranking}

Bayesian ranking runs only after a deterministic invariant result exists. It is
used to order findings in the report, assign posterior-mode labels, and decide
which issue candidates or probes appear first. It is not used to create a
failure. Operationally, the pipeline is: \tool generates or accepts a candidate
scenario; contract validation rejects malformed or non-applicable candidates;
the connector executes valid probes or returns observed evidence; a deterministic
invariant produces \(\Pass\) or \(\Fail\); and only then does \tool compute
\(\rho_i\). Thus Bayesian ranking answers which verified finding a tester should
inspect first. It does not answer whether the behavior is a bug.

For catalog and generated verifier scenarios, the ranking inputs come from two
places: invariant metadata and connector/context observations. In the current
implementation the invariant metadata is the \texttt{Invariant} object:
\[
  I_i =
  (\texttt{id},\texttt{expected},\pi_i,L_i^{fail},L_i^{pass},
   \texttt{difficulty},\phi_i).
\]
The \tool-authored catalog stores these objects in
\texttt{bayesilisk/invariants.py}; report output serializes the same likelihood
metadata as \texttt{failLikelihood} and \texttt{passLikelihood}. Thus
\(\pi_i\), \(L_i^{fail}\), and \(L_i^{pass}\) are not inferred during a run.
They are prior/ranking constants supplied by the invariant author with the
invariant definition; they are not generated by the LLM and are not derived from
connector execution. For connector-defined invariants, the same role is played
by the connector's declared invariant metadata.

The run-time context adjustment is computed from observation tags and explicit
context fields. For finding fingerprint \(x\), invariant \(i\), and scenario
\(s\), the implementation computes
\[
  \Delta_i =
  -0.28\,\mathbf{1}_{x\in Fixed}
  +0.18\,\mathbf{1}_{x\in Confirmed}
  -0.45\,\mathbf{1}_{x\in Muted}
  +A_i+B_s,
\]
where \(x\) is the finding fingerprint, \(A_i\) is an explicit context
adjustment for invariant \(i\), and \(B_s\) is an explicit context adjustment
for scenario \(s\); missing explicit adjustments are zero. The sets
\(Fixed\), \(Confirmed\), and \(Muted\) are populated from
\texttt{fixedFingerprints}, \texttt{confirmedFingerprints}, and
\texttt{mutedFingerprints} in the context/observation file, plus fingerprints
extracted from that context. \(A_i\) is read from the context field
\texttt{priorAdjustments}; \(B_s\) is read from \texttt{scenarioAdjustments}.
If these fields are absent or malformed, their contribution is zero.

The likelihood used in the posterior is selected after deterministic
verification. For a concrete scenario \(s\), \tool merges its fragments into
facts \(F_s\) and calls the invariant evaluator:
\[
  \phi_i(F_s) \rightarrow (b_i,o_i),
\]
where \(b_i\) is the Boolean evaluator result and \(o_i\) is the evaluator's
observation text. The reported deterministic result is
\[
  r_i =
  \begin{cases}
    \Pass & \text{if } b_i=\texttt{true},\\
    \Fail & \text{if } b_i=\texttt{false}.
  \end{cases}
\]
Only then does \tool choose the scalar likelihood used for ranking:
\[
  \ell_i =
  \begin{cases}
    L_i^{pass} & \text{if } r_i=\Pass,\\
    L_i^{fail} & \text{if } r_i=\Fail.
  \end{cases}
\]
So ``computed'' here means deterministic branch selection from invariant
metadata after the evaluator has already returned pass/fail. There is no learned
likelihood estimator in the current artifact, and the likelihood does not
decide whether the scenario failed. It only changes the ordering of already
evaluated findings. The adjusted prior is
\[
  \tilde{\pi}_i = \operatorname{clip}_{[0.05,0.95]}(\pi_i + \Delta_i).
\]
The posterior risk score is
\[
  \rho_i =
  \frac{\tilde{\pi}_i \ell_i}
       {\tilde{\pi}_i \ell_i + (1-\tilde{\pi}_i)(1-\ell_i)}.
\]
This is a ranking score in the Bayesian sense~\cite{bishop2006pattern}. The
report sorts by decreasing \(\rho_i\), then by posterior mode and finding id,
so \(\rho_i\) controls report order, follow-up probe order, and triage labels.
Pass/fail is produced only by the invariant evaluator.

Direct connector-observed findings use the same general report pipeline but a
different scoring path. If connector evidence already contains a deterministic
mismatch between expected and observed status, the finding is evidence-bearing
before Bayesian ranking. \tool records it as a context-observed breakage, marks
it issue-ready, and gives it high report priority. This is evidence-first
ranking, not learned Bayesian inference. The path is connector-generic; Cal.com
is the current case study using it, not a special rule in the core.

\subsection{Evidence Verification}

Execution is a connector function
\[
  X_C(s) \rightarrow e,
\]
where \(e\) is observed evidence. For the Cal.com connector, the core evidence
fields are \(\texttt{expectedStatus}\), \(\texttt{observedStatus}\), route,
target URL, invariant id, and source context. The verifier applies
\[
  \phi_i(e) =
  \begin{cases}
    \Fail & \text{if } e.\texttt{observedStatus} \ne e.\texttt{expectedStatus},\\
    \Pass & \text{if } e.\texttt{observedStatus} = e.\texttt{expectedStatus},\\
    \Invalid & \text{if required evidence is absent or malformed.}
  \end{cases}
\]
Only \(\Fail\) with evidence becomes an issue-ready finding. \(\Invalid\) is a
connector/proposer diagnostic.

\section{Implementation Boundary}

\tool implements separate ledgers for provenance, attention, proposal, execution
evidence, and verification. The provenance ledger records which repository,
source claims, fixture boundary, and connector contract produced a run. The
attention ledger records which invariant planes should be explored. The
model-proposal ledger records accepted and rejected model proposals. The
execution-evidence ledger records connector-returned observations. The
verification ledger records deterministic invariant outcomes, fingerprints,
issue readiness, and risk scores. Only the verification ledger contains
issue-ready pass/fail results.

This boundary matters for connector design. A connector should expose a small
vocabulary of actions and facts. It should not filter away uncomfortable cases
or decide that a 200 response is acceptable. The finite-state verifier owns the
ruleset, which is supplied by context and schema, not hardcoded for a particular
application. App-specific code is isolated to connector execution.

The agent-facing workflow is therefore a packaging of the same proof boundary,
not a new oracle. A coding agent can interview for connector requirements,
record provenance, produce a connector prompt packet, propose a scenario plan,
and draft a fix brief. The verifier accepts those artifacts only as context or
candidate input. Concrete observations must still come from connector
execution, and fix briefs must still trace to verified issue-ready findings.

\subsection{Surface Scanning and the Automated Loop}

\tool can derive the contract surface deterministically: a scanner maps each
path and operation of an API description to a route fact with typed parameters
(identifier, tenant, and token kinds with their abstract tokens), yielding a
draft contract \(C\) that the motif binder expands. The full procedure is exposed
as a stateless loop controller. Given the current artifacts it performs every
deterministic step---scan, motif binding, contract validation, evidence
verification, and repair-brief synthesis---advances a convergence state, and
returns the one action it cannot perform: connector execution. The agent or human
supplies observed evidence; the controller verifies it, accumulates verified
issue-ready fingerprints, and stops when \(K\) consecutive rounds add no new such
fingerprint or a round cap is reached. The controller holds no session and is
deterministic; it automates the boundary above without \tool ever executing the
application or deciding the verdict.

\section{Cal.com Case Study}

We evaluated the current connector architecture on a local Cal.com
checkout~\cite{calcom}.
The tested repository and revision were:

\begin{itemize}
  \item Repository: \url{https://github.com/calcom/cal.com}
  \item Commit: \texttt{180ede28f0bddf2738933a6e60a8e80f6116d7da}
  \item Commit date: \texttt{2026-05-14 19:30:21 +0000}
  \item Commit subject: font-stack fallback fix for non-Latin script support
        (\texttt{\#29346})
  \item Bayesilisk seed: \texttt{150}
\end{itemize}

The connector supplied three route facts for booking pages with
\texttt{rescheduleUid} behavior and one typed ABAG for a longer booking
workflow. \tool generated six route-mutation probes and one workflow-sequence
probe. The sequence was:
\[
  \texttt{create-booking} \rightarrow
  \texttt{cancel-booking} \rightarrow
  \texttt{open-public-booking-route}.
\]

The ABAG was not Cal.com logic embedded in the \tool core. The checked-in
connector acted as an adaptor. Its \texttt{create-booking} action produced four
abstract-to-concrete refinements:
\begin{itemize}
  \item \texttt{resource.public\_id}/\texttt{booking}
        \(\mapsto\) \texttt{booking.uid};
  \item \texttt{resource.id}/\texttt{booking}
        \(\mapsto\) \texttt{booking.id};
  \item \texttt{resource.public\_id}/\texttt{event\_type}
        \(\mapsto\) \texttt{eventType.slug};
  \item \texttt{principal.actor}/\texttt{calcom\_user}
        \(\mapsto\) \texttt{user.username}.
\end{itemize}
The \texttt{cancel-booking} action required
\texttt{resource.id}/\texttt{booking} and produced
\texttt{state.cancelled}/\texttt{booking}. The
\texttt{open-public-booking-route} action bound \texttt{rescheduleUid} to
\texttt{resource.public\_id}/\texttt{booking}.
\tool matched only the abstract keys and generated the sequence. The Cal.com
Playwright connector used the \texttt{refines} names to execute real fixture
operations and return observed status evidence.

\section{Scope and Generalization}

\tool is intended to be adopted through app-specific connectors and
app-agnostic verification. The following points describe that engineering
boundary and the evidence needed to broaden the empirical case; they are not
exceptions to the architecture.

\textbf{Application scope.} The current public practical validation is Cal.com.
The result does not depend on Cal.com-specific verifier code: the core consumes
a connector contract and generated probes through the same app-agnostic
interfaces used elsewhere in \tool. Additional application artifacts would
strengthen empirical breadth, but the required adaptation is the expected one:
each app team writes a connector that exposes its own routes, actions, state
facts, fixtures, and invariants.

\textbf{Connector specificity.} Connector-specific code is not a weakness of the
architecture; it is the integration boundary. A team that knows the app
specification can declare actors, routes, action hooks, identifiers, and
invariants without modifying the \tool core. Connector quality still matters:
the broader and more accurate the declared surface, the broader the generated
probe space.

\textbf{Agent-assisted adoption.} The intended adoption path is compatible with
coding agents, but not dependent on trusting them. An agent can be guided to
read existing tests and route handlers, write connector source context, and
implement action mappings in the target repository. The contract prevents that
agent from also becoming the oracle: generated plans are checked for
verifier-owned fields, provenance is recorded before execution, and any repair
brief is downstream of deterministic verification.

\textbf{ABAG refinement boundary.} Typed ABAG tokens are the portability layer.
The \tool core matches \texttt{token} and optional \texttt{resourceType}. It does
not treat \texttt{refines} as evidence that a dependency is satisfied.
\texttt{refines} is deliberately adaptor-local: it carries concrete names that
the connector needs to execute a probe, such as fixture fields, URL parameters,
database ids, or session handles. This keeps Cal.com names out of the verifier
while still letting the generated proposal be executable.

\textbf{Bounded workflow generation.} Sequence generation is intentionally
bounded by the connector-declared action graph and depth. That bound can still
cover a large workflow space when the connector exposes a broad action
vocabulary and meaningful state tokens. The design avoids arbitrary free-form
browser wandering; \tool composes declared actions and the connector executes
them.

\textbf{Oracle scope.} The deterministic oracle is only as good as the supplied
ruleset. \tool prevents the LLM from being the oracle; it does not remove the
need for correct invariants.

\textbf{Baseline interpretation.} The Cal.com comparison runs validate the
architectural difference: nearby E2E did not cover the generated states, manual
Playwright probes were narrower, weak local model output was rejected by
validation, and browser-driving LLM trials showed oracle instability. A larger
multi-app study would quantify effect size across projects and models; it is
not required to establish the core separation demonstrated here.

\section{Future Work}

Two next steps would make the ranking layer more mathematically grounded while
preserving the same trust boundary: attention and probability may guide search,
but they must not become the oracle.

\textbf{Actual Grassmann attention.} The current implementation uses
\(\alpha_i\), a bounded anchor-plane proxy for the ideal Grassmannian score
\(\gamma_i(q)\). A fuller version should construct an explicit feature vector
\(q\) for each connector context and an orthonormal basis \(U_i\) for each
invariant subspace \(P_i\). The operational attention score could then be the
projection energy
\[
  \gamma_i(q)=\|U_i^\top q\|_2^2,
\]
or a related Grassmann distance based on principal angles between the context
subspace and invariant subspace. The basis vectors can be built from invariant
text, connector-declared routes/actions, nearby tests, execution evidence, and
validated historical findings. This would replace the current hand-weighted
proxy as the main exploration router, while leaving deterministic verification
unchanged~\cite{edelman1998geometry}.

\textbf{Calibrated likelihoods.} The current artifact uses invariant-level
ranking constants \(L_i^{fail}\) and \(L_i^{pass}\). A stronger version should
estimate likelihoods from validation data. Let \(Z_i\) mean that invariant
\(i\) is genuinely violated, and let \(r_i\in\{\Pass,\Fail\}\) be the
deterministic verifier result. For a failing result, the calibrated posterior
should use
\[
  P(Z_i\mid r_i=\Fail)=
  \frac{P(Z_i)P(r_i=\Fail\mid Z_i)}
       {P(Z_i)P(r_i=\Fail\mid Z_i)+
        P(\neg Z_i)P(r_i=\Fail\mid \neg Z_i)}.
\]
The terms \(P(r_i=\Fail\mid Z_i)\) and
\(P(r_i=\Fail\mid \neg Z_i)\) are the true-positive and false-positive behavior
of that verifier/probe family. They can be estimated from historical
Bayesilisk findings, seeded faults, negative controls, connector evidence
quality, invariant class, and human validation signals such as upstream issue
acceptance, fix pull requests, and regression tests. Passing controls should be
calibrated analogously with \(P(r_i=\Pass\mid Z_i)\) and
\(P(r_i=\Pass\mid \neg Z_i)\). This would turn the current hand-calibrated
ranking constants into empirical reliability estimates without changing the
rule that pass/fail is decided only by deterministic invariants~\cite{bishop2006pattern,guo2017calibration}.

\section{Conclusion}

\tool treats LLMs and coding agents as scenario proposers, not as test oracles.
The mathematical boundary is simple: candidate generation and attention may be
probabilistic or heuristic, but validation and verification are deterministic
functions over a connector-declared contract and connector-returned evidence.
The Cal.com case study demonstrates that this separation can produce useful
real-app findings: seven generated probes, seven observed invariant violations,
issue-ready payloads, and a review-approved upstream fix PR for one reported
issue. The
adoption path is incremental: write the connector around existing app fixtures,
or have a coding agent draft it under recorded provenance, let \tool expand the
scenario space, and keep the oracle deterministic. Packaging the surface as a
category-theoretic motif library, a deterministic scanner, and a stateless loop
controller makes that surface reusable across apps and runs the
scan--verify--repair cycle to convergence without moving the oracle. The next
research step is to repeat this artifact discipline across additional
applications while keeping the \tool core app-agnostic.
